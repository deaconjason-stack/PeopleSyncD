# M2.4 Passkey and Privileged-Reauthentication Security Model

## Trust boundary

WebAuthn private keys stay in the platform authenticator, roaming security key, or synced passkey provider. PeopleSyncD receives public credential material and signed WebAuthn responses only.

The server validates ceremonies through the configured relying-party ID and accepted origins. Development defaults are `localhost` and `http://localhost:3000`; these are not production configuration values.

## Required verification

Registration and assertion options require WebAuthn user verification. Registration requests a resident credential. Attestation conveyance is `none`, so this milestone does not establish hardware provenance or enterprise attestation trust.

## Persisted data

Passkey records contain credential ID, public key, user handle, signature counter, AAGUID, backup-state metadata, display name, and timestamps. No authenticator private key, PIN, biometric template, password, access token, or refresh token is written to a passkey record.

Ceremony records contain server-generated WebAuthn options, user and optional tenant context, purpose, expiry, and completion timestamp. Ceremony state is short-lived and single-use.

## Replay and concurrency

WebAuthn assertion verification supplies the stored signature counter to the FIDO2 verifier. PeopleSyncD persists the returned counter and conditionally updates the credential state. The ceremony itself is also completed conditionally on PostgreSQL. Synced passkeys may legitimately report a zero counter; single-use challenge state remains the primary replay boundary for such credentials.

## Account enumeration

The initial passwordless flow is email-first. Unknown users and known users without an active passkey receive the same `authentication.passkey_unavailable` application error.

## Session assurance

Successful passkey authentication issues `phishing_resistant` assurance with `amr=passkey`. Refresh rotation preserves the original `auth_time` and authentication method. Refreshing a session cannot satisfy a five-minute privileged-operation window.

## Privileged actions

M2.4 applies the five-minute freshness requirement to passkey enrollment/revocation and organization invitation/membership mutation. This is an initial policy set, not a claim that every future high-impact operation is already classified.

## Remaining risk and release boundaries

Before production approval, PeopleSyncD still requires production RP/origin configuration, browser-session hardening, operational review, live-authenticator acceptance, penetration testing, backup/recovery review for identity data, signed release packaging, and explicit deployment approval.
