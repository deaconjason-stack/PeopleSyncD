# M2.2 Session and Invitation Security Model

## Invitation secrets

Invitation bearer tokens use cryptographically secure random bytes. Only SHA-256 hashes are stored in the database. Invitations are single-use, expire after seven days, and cannot grant the Owner role.

## Membership authority

Organization membership is checked against live persistence for every tenant-scoped request. A token is rejected when its membership is no longer active, its user or organization does not match, or its role differs from the current persisted role. This closes the stale-JWT window after role, suspension, or revocation changes.

The final active Owner cannot be demoted, suspended, or revoked through the generic membership endpoint. Owner promotion is intentionally deferred to a dedicated ownership-transfer workflow.

## Email verification

Password authentication may establish a user session before email verification, but tenant-scoped permissions require the `email_verified=true` claim. Invitation acceptance is treated as control of the invited email bearer secret and marks the created or matched account verified.

## Refresh tokens

Refresh tokens are 48 random bytes encoded for transport. Only SHA-256 hashes are persisted. Every successful use marks the old session used and creates one replacement in the same family. Reuse of a previously used token revokes the entire family and records a security audit event. A unique parent-session constraint protects relational deployments from concurrent double rotation.

Membership role or status changes revoke refresh sessions bound to that membership. Refresh processing also re-checks the current account and membership before minting a new access token.

## MFA boundary

M2.2 does not claim completed MFA. It establishes a fail-closed boundary: if ASP.NET Core Identity reports that two-factor authentication is enabled, password-only login and refresh continuation are denied until the future step-up flow is completed.

## Audit minimization

Security audit records contain event type, actor, optional tenant, target reference, timestamp, and small non-secret metadata. Invitation tokens, refresh tokens, passwords, signing keys, and email-verification tokens are never written to audit metadata.
