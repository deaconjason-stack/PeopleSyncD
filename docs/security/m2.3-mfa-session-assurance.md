# M2.3 MFA and Session Assurance Security Model

## Scope

M2.3 adds executable TOTP multi-factor authentication, single-use recovery codes, short-lived MFA challenges, assurance-aware sessions, live session revocation, and a user-facing security center to the .NET platform path.

This milestone implements TOTP and recovery-code verification only. WebAuthn/passkeys are not implemented by M2.3.

## TOTP enrollment

An authenticated user can request TOTP enrollment material. PeopleSyncD uses the ASP.NET Core Identity authenticator-key store and returns a standards-compatible `otpauth://` URI plus the manual Base32 entry key.

MFA is not activated merely because an authenticator secret was issued. The user must submit a valid RFC 6238 code that proves possession of the authenticator before `TwoFactorEnabled` becomes true.

The interoperable authenticator profile uses 30-second, six-digit TOTP with HMAC-SHA1 as defined by the established RFC 6238 authenticator ecosystem. SHA-1 is not used as a general PeopleSyncD storage hash. MFA challenge bearer secrets, invitation secrets, refresh secrets, and recovery codes use SHA-256 hash-only storage where their verification model permits it.

The TOTP authenticator secret itself cannot be hash-only because TOTP verification requires the shared secret. It is therefore sensitive secret material held by the ASP.NET Core Identity token store. Production certification requires protected database storage, encryption controls, backup protection, and production key custody appropriate to this secret.

## TOTP replay prevention

PeopleSyncD persists the highest accepted TOTP moving-factor counter in `mfa_totp_states`. A newly matched TOTP counter must advance beyond the stored counter before the factor can succeed.

PostgreSQL uses an atomic `INSERT ... ON CONFLICT ... DO UPDATE ... WHERE` counter advance. A concurrent request using the same or an older accepted counter receives no successful advance and is denied. Replay denial emits `identity.mfa.totp_replay_denied` without recording the submitted code.

The same single TOTP code therefore cannot be reused successfully across two different login challenges while it remains inside the accepted clock window.

## MFA challenge lifecycle

MFA challenges use 32 cryptographically random bytes encoded as Base64URL. Only SHA-256 hashes of challenge bearer secrets are stored.

Challenge controls:

- five-minute lifetime;
- purposes limited to `login` and `step_up`;
- organization and membership context must be supplied together;
- maximum five failed attempts;
- conditional atomic completion on PostgreSQL;
- completed challenges cannot be replayed;
- factor codes are never written into the security audit record.

A password-authenticated user with MFA enrolled receives a challenge instead of an access token. Tenant authority is not issued until the challenge succeeds.

## Recovery codes

MFA activation generates ten random recovery codes. Raw recovery codes are returned to the user only in the generation response. PeopleSyncD stores normalized SHA-256 hashes, not the raw codes.

Recovery-code consumption is single-use. PostgreSQL performs an atomic conditional update where `UsedAt` and `RevokedAt` are null, so simultaneous use has at most one successful consumer.

Regenerating recovery codes revokes every previously unused code before the new batch is returned.

## Session assurance

Access tokens carry:

- `sid` — the server-backed refresh-session family identifier;
- `psd_assurance` — `pwd` or `mfa`;
- `amr` — password and, when applicable, MFA authentication methods;
- `auth_time` — token authentication time.

Refresh-session rows retain the assurance level and a bounded client `User-Agent` label. M2.3 deliberately does not persist client IP addresses in the session inventory.

When MFA is enabled, all earlier refresh sessions are revoked. A user must sign in again and complete MFA to obtain an MFA-assured session.

An MFA-enrolled user cannot refresh a password-only session. The family is revoked and reauthentication is required.

## Live revocation

Authenticated requests pass through `AccountSecurityValidationMiddleware` before tenant-membership validation. The middleware revalidates:

- the account still exists and is active;
- the token carries a session-family identifier;
- the session family still has an active, unused, unrevoked, unexpired refresh row;
- an MFA-enrolled account is using an MFA-assured access token.

This makes explicit session revocation and MFA-enrollment session invalidation effective on the next authenticated request rather than waiting for the access JWT to expire.

Tenant membership is still revalidated separately, preserving the M2.2 stale-role and stale-membership protections.

## Step-up boundary

M2.3 exposes a fresh `step_up` MFA challenge and can issue a new MFA-assured session after successful verification. It does not yet bind individual high-impact business operations to a maximum authentication age. Policy-specific freshness requirements remain a later authorization increment.

## Browser custody boundary

The M2 browser stores only the access token in `sessionStorage`. It does not persist refresh tokens. Production browser certification still requires a hardened backend-for-frontend or equivalent secure HTTP-only cookie custody model before refresh tokens are entrusted to the browser channel.

## Production boundaries not claimed by M2.3

M2.3 does not certify:

- WebAuthn, passkeys, or phishing-resistant authenticators;
- production identity-provider federation;
- production notification delivery;
- production encryption or signing-key custody;
- hardened browser refresh-token custody;
- security operations approval;
- signed release packaging;
- production deployment approval;
- SOC 2, HIPAA, government, or other regulatory certification.
